# REVIEW.md

Правила код-ревью для этого монорепо. Файл описывает **как ревьюить PR** — процесс, критерии,
формат замечаний. Как устроен код и почему — в `CLAUDE.md` (корневой и по приложениям);
здесь на них ссылки, а не дубликаты.

Читают файл и человек-ревьюер, и Claude Code (`/review <PR>` для чужого PR, `/code-review` для
своего рабочего диффа).

## Процесс

- В `master` попадают только изменения через PR (GitHub Flow — см. корневой `CLAUDE.md`).
- PR ревьюится целиком по `git diff master...HEAD` (**три точки** — только изменения ветки).
- Ревью начинается после зелёных проверок. Красный CI — ревью не делаем, возвращаем автору.
- Мерж — squash после апрува; ветка удаляется.

### Перед тем как звать ревьюера (обязанность автора)

```bash
npm run typecheck
npm run lint
npm test
npm run test:e2e        # если трогал apps/api; нужен поднятый контейнер БД
```

Если что-то из этого не запускалось — так и напиши в PR, в секции `## Testing`. Ревьюер вправе
вернуть PR без разбора, если проверки не прогнаны.

### Обязанность ревьюера

- Проверить, что описание PR соответствует диффу: заголовок по Conventional Commits, секции
  `Summary` / `API` / `Frontend` / `Breaking changes` / `Testing` на английском, лишние секции
  выкинуты.
- Прочитать дифф целиком, а не только новые файлы: удалённые строки — тоже изменение.
- Проверить не «нравится/не нравится», а по критериям ниже. Всё, что вне списка блокирующих
  правил, — это `nit`, и оно не блокирует мерж.

## Уровни замечаний

Каждое замечание помечается уровнем — автору должно быть однозначно ясно, что чинить обязательно.

| Уровень   | Значение                                                        | Блокирует мерж |
| --------- | --------------------------------------------------------------- | -------------- |
| `blocker` | нарушение правила из «Блокирующих», баг, дыра в безопасности      | да             |
| `major`   | архитектурное расхождение, отсутствие теста на новую логику       | да             |
| `minor`   | дубль, неудачное имя, мёртвый код                                 | нет, но чиним  |
| `nit`     | вкусовщина, форматирование                                        | нет            |

Формат замечания: **что не так → почему это проблема → что сделать**. Без «переделай». Ссылку
на правило (`apps/api/CLAUDE.md`, раздел «Конвенции») давать явно.

## Блокирующие правила

Нарушение любого — `blocker`, независимо от размера PR.

### Общие

1. **Денежные суммы — строки.** В БД `Decimal(12,2)`, наружу `amount.toFixed(2)`. Приведение к
   `number` где угодно (сервис, DTO, компонент, расчёт на клиенте) — блокер: теряются копейки.
2. **Замороженные версии не поднимаются.** `typescript` 5.9.3, `eslint` 9.39.5, swc-трансформ в
   Vitest вместо Oxc. Бамп в `package.json` или снятие `oxc: false` — блокер, пока в описании PR
   нет отдельного обоснования и прогона всех сборок.
3. **Секреты не коммитятся.** `.env` не в гите; новые переменные добавляются в `.env.example` с
   плейсхолдером и упоминаются в PR.
4. **Публичные контракты меняются осознанно.** Изменился формат ответа эндпоинта или экспорт
   `@repo/shared` — в заголовке PR `!`, в описании секция `Breaking changes` с тем, что чинить
   потребителю.
5. **Изменения в схеме Prisma идут вместе с миграцией.** Правка `schema.prisma` без файла в
   `packages/db/prisma/migrations/` — блокер. Паттерны Prisma 6 (`url` в `datasource`,
   `new PrismaClient()` без адаптера, генератор `prisma-client-js`) — тоже.

### apps/api

6. **`userId` берётся из токена, а не из query/body.** `@CurrentUser()` + `@UseGuards(JwtAuthGuard)`.
   Появившийся в диффе `?userId=` или чтение id пользователя из тела запроса — дыра: позволяет
   читать чужие данные.
7. **Новый защищённый контроллер = `@UseGuards(JwtAuthGuard)` + импорт `AuthModule`.** Глобального
   guard'а нет намеренно (`/api/auth/register` и `/api/auth/login` публичные). Контроллер без
   guard'а — блокер, если эндпоинт работает с данными пользователя.
8. **Фильтр по `userId` в сервисе не снимается.** Любой запрос к транзакциям/категориям
   фильтруется по владельцу. Изоляция покрыта e2e — падающий e2e на изоляции чинится, а не
   переписывается под новое поведение.
9. **`ZodValidationPipe` вешается на параметр**, а не через `@UsePipes` на методе — иначе
   валидируются все аргументы, включая query-строки. Этот баг уже был.
10. **Граница Users ↔ Auth — только CQRS.** Импорт `UsersModule` в `AuthModule`/`CategoriesModule`/
    `TransactionsModule` или инъекция `UsersService`/`UsersRepository` наружу — блокер. Общение
    через `CommandBus`/`QueryBus` и контракты из `users/contracts/`.
11. **Валидация новых модулей — zod.** class-validator в `categories`/`transactions` — зафиксированное
    исключение, не образец. Новый модуль на class-validator — `major`, требует обоснования в PR.
12. **Хэш пароля не покидает бэкенд.** Наружу только `UserDto { id, email, name }`. Ограничение
    пароля в 72 символа не снимается (bcrypt молча режет хвост).
13. **`tsconfig` API сохраняет `experimentalDecorators`, `emitDecoratorMetadata`,
    `isolatedModules: false`.** Снятие ломает DI молча.

### apps/web

14. **Слои FSD импортируются только вниз** (`app → views → widgets → features → entities → shared`).
    Импорт вверх или к соседу того же уровня — блокер. Обращение внутрь чужого слайса в обход его
    `index.ts` — тоже.
15. **JWT не уходит на клиент.** Токен живёт в httpOnly-куке `session`; клиент ходит только в свои
    Route Handlers, наружу отдаётся `{ user }`. Любой `accessToken` в ответе BFF, в пропсах или в
    сторе — блокер.
16. **Серверные модули помечены `import "server-only"`** и не реэкспортируются из клиентского
    `index.ts` слайса (для `session` серверный вход — `server.ts`). Утечка серверного модуля в
    клиентский бандл — блокер.
17. **Источник истины по сессии — `getSession()`.** Гард на `/login` и `/register` — в серверном
    `page.tsx`. Проверка «есть кука» вместо `getSession()` даёт петлю редиректов на протухшем
    токене — блокер.
18. **Route Handlers остаются тонкими обёртками.** Бизнес-логика в `app/api/**/route.ts` — `major`,
    её место в слайсе.

## Что смотреть помимо правил

Это не блокирует автоматически, но именно здесь ревью приносит пользу.

- **Тесты на новую логику.** Новый сервис/ветка поведения без `*.spec.ts` — `major`. Новый или
  изменённый эндпоинт без e2e — `major`. Тест, проверяющий мок вместо поведения, — `minor`.
- **Ошибочные пути.** Что вернёт эндпоинт на несуществующем id, чужом id, пустом списке; что
  покажет форма на 401/409/400. Ошибки бэкенда пробрасываются со статусом и `message`.
- **Соответствие e2e и `main.ts`.** Менялся бутстрап (глобальный префикс, `ValidationPipe`) —
  тестовое приложение должно быть настроено так же, иначе тестируется не прод.
- **Границы транзакций и N+1.** Несколько записей одной операцией — в транзакции; выборки в цикле
  вместо одного запроса — `minor`/`major` по масштабу.
- **Размер PR.** Больше ~400 изменённых строк осмысленной логики — попроси разбить, если это не
  один неделимый рефакторинг.
- **Мёртвый код и закомментированные куски** не мержатся: история есть в гите.
- **Комментарии-«почему».** В этом репо много неочевидных решений (порт 5433, отсутствующий импорт
  `UsersModule`, `oxc: false`). Если PR добавляет такое же неочевидное — комментарий обязателен,
  иначе следующий разработчик это «починит».

## Чего в замечаниях быть не должно

- Правок стиля, которые сделает `lint`/`prettier`. Форматирование не обсуждаем.
- «А ещё вот тут отрефактори» про код вне диффа — заводи отдельную задачу.
- Переспора о решениях, уже зафиксированных в `CLAUDE.md` (class-validator в двух модулях, порт
  5433, замороженные версии). Хочешь поменять — отдельный PR с правкой документации.
- Перечисления одного и того же в десяти местах: одно замечание + «то же в ещё N местах».

## Чеклист ревьюера

```
[ ] git diff master...HEAD прочитан целиком
[ ] заголовок PR по Conventional Commits, breaking помечен `!`
[ ] описание PR на английском и соответствует диффу
[ ] typecheck / lint / test зелёные; e2e прогнаны, если трогали api
[ ] деньги не стали number нигде
[ ] userId из токена, фильтр по владельцу на месте
[ ] новые защищённые эндпоинты под JwtAuthGuard
[ ] FSD: импорты только вниз, слайсы через index.ts
[ ] токен не утёк на клиент, server-only на месте
[ ] схема Prisma + миграция вместе
[ ] новая логика покрыта тестами, ошибочные пути тоже
[ ] нет мёртвого кода, замороженные версии не тронуты
[ ] .env.example обновлён, если добавились переменные
```

## Апрув

- **Approve** — блокеров и major нет; minor/nit оставлены как есть или поправлены на месте.
- **Request changes** — есть blocker или major.
- **Comment** — вопросы к автору, решение после ответа.

После апрува мержит автор: squash, заголовок squash-коммита — заголовок PR, без футеров и
упоминаний Claude/Co-Authored-By.
