# Документация проекta «Трекер расходов»

Этот документ отвечает на вопросы «почему тут так устроено»

---

## 1. Что это за проект и из чего он собран

Это **монорепозиторий** (монорепо) — один git-репозиторий, внутри которого живёт
сразу несколько отдельных приложений и библиотек. У нас их четыре:

| Что             | Где лежит         | Технология            | Роль                                            |
| --------------- | ----------------- | --------------------- | ----------------------------------------------- |
| Фронтенд (сайт) | `apps/web`        | Next.js 16 + React 19 | То, что видит пользователь в браузере (`:3000`) |
| Бэкенд (API)    | `apps/api`        | NestJS 11             | Сервер, который отдаёт данные по HTTP (`:3001`) |
| Слой БД         | `packages/db`     | Prisma 7              | Схема таблиц + клиент для работы с PostgreSQL   |
| Общий код       | `packages/shared` | zod                   | Схемы валидации и типы, общие для фронта и бэка |

Плюс PostgreSQL в Docker-контейнере (`:5433`) — это база данных, а не код проекта.

Ключевая идея монорепо: **фронт и бэк должны договориться о формате данных**.
Если поле называется `amount` и это строка — оба должны знать об этом одинаково.
Вместо того чтобы копировать типы туда-сюда, мы держим их в одном месте
(`packages/shared`) и подключаем в обоих приложениях. Один источник правды.

## 3. Почему несколько `package.json`, но `node_modules` фактически одна

Это твой главный вопрос — разберём медленно.

### 3.1. Что такое `package.json`

`package.json` — это «паспорт» одного пакета: как он называется, от чего зависит,
какие у него команды (`scripts`). **Правило: один пакет = один `package.json`.**

У нас пакетов не один, а пять, поэтому и файлов пять:

1. **Корневой** (`/package.json`) — паспорт всего монорепо. Он _не_ описывает
   приложение, у него особая роль: в нём есть поле `workspaces`, которое говорит
   npm «внутри меня живут ещё пакеты, ищи их в `apps/*` и `packages/*`».

   ```json
   "workspaces": ["apps/*", "packages/*"]
   ```

2. **`apps/web/package.json`** — паспорт фронтенда (`@repo/web`): зависит от `next`,
   `react`, и от нашего `@repo/shared`.
3. **`apps/api/package.json`** — паспорт бэкенда (`@repo/api`): зависит от `@nestjs/*`,
   а также от `@repo/db` и `@repo/shared`.
4. **`packages/shared/package.json`** — паспорт общей библиотеки (`@repo/shared`).
5. **`packages/db/package.json`** — паспорт слоя БД (`@repo/db`).

Каждый должен объявлять СВОИ зависимости честно, потому что когда-нибудь эти пакеты
можно вынести и опубликовать отдельно. Фронт не должен «случайно» пользоваться тем,
что установил бэк.

### 3.2. Почему тогда `node_modules` одна

Здесь работает механизм npm под названием **hoisting** (подъём зависимостей).

Когда ты запускаешь `npm install` в корне, npm:

1. Читает `workspaces` и находит все пять `package.json`.
2. Собирает **все** их зависимости вместе.
3. Складывает их в **одну** корневую `node_modules/` — «на верхний этаж».

Смысл: если и фронт, и бэк используют, например, `zod@4.4.3` — глупо скачивать его
дважды. npm ставит его один раз в корень, а оба приложения его оттуда видят
(Node.js при `import` ищет `node_modules` вверх по дереву папок, пока не найдёт).

> В проекте формально есть ещё маленькие `node_modules` внутри воркспейсов
> (`apps/api/node_modules`, `packages/db/node_modules`, `packages/shared/node_modules`),
> но если заглянуть внутрь — там **нет пакетов**, только кэши инструментов
> (`.vite`, `.cache`). Все настоящие зависимости подняты в корень. Так что твоё
> ощущение «node_modules одна» — по сути правильное.

### 3.3. Магия `@repo/*`: как приложения видят наши библиотеки

Открой `apps/api/package.json` — там среди зависимостей:

```json
"@repo/db": "*",
"@repo/shared": "*"
```

`"*"` значит «любая версия» — потому что это не пакет из интернета, а наш локальный.
При установке npm видит, что `@repo/db` — это workspace, и вместо скачивания создаёт
**символическую ссылку** (ярлык):

```
node_modules/@repo/db  →  packages/db
node_modules/@repo/shared → packages/shared
```

Поэтому в коде можно писать:

```ts
import { createExpenseSchema } from "@repo/shared"; // на самом деле packages/shared
import { createPrismaClient } from "@repo/db"; // на самом деле packages/db
```

…и это работает как обычный npm-пакет, хотя код лежит прямо в репозитории. Изменил
файл в `packages/shared` — оба приложения сразу видят изменения (после пересборки).

### 3.4. Один `package-lock.json`

Замок версий (`package-lock.json`) тоже **один на весь монорепо**. Он фиксирует
точные версии _всех_ пакетов _всех_ воркспейсов, чтобы у тебя и у коллеги
установилось абсолютно одинаковое. Это прямое следствие того, что установка — общая.

## 4. Зачем бэкенд и фронтенд завёрнуты в папку `apps/`

Это чисто организационное деление, но очень полезное. В монорепо принято разделять:

- **`apps/`** — то, что **запускается** и является конечным продуктом
  («приложения»). У нас это `web` (сайт) и `api` (сервер). Их можно задеплоить.
- **`packages/`** — то, что **не запускается само**, а **используется** приложениями
  («библиотеки»). У нас это `shared` (типы/схемы) и `db` (доступ к базе).

Зачем это нужно:

1. **Понятность.** С первого взгляда видно: `apps/` — «мозг, который работает»,
   `packages/` — «детали, из которых он собран».
2. **Правило зависимостей.** Приложения зависят от библиотек, но не наоборот, и
   библиотеки не зависят друг от друга как попало. Граф у нас такой:

   ```
   web  ──→ shared
   api  ──→ shared
   api  ──→ db
   ```

   `apps/` могут импортировать из `packages/`, но `packages/` ничего не знают про
   `apps/`. Это удерживает архитектуру от превращения в «кашу».

3. **Настройка инструментов.** В `turbo.json` и `workspaces` удобно писать
   `apps/*` и `packages/*` вместо перечисления каждого руками.

> Технически можно было положить `web` и `api` прямо в корень. Папка `apps/` — это
> соглашение (конвенция), а не требование инструмента. Но соглашение хорошее, и его
> придерживается почти вся индустрия (так же устроены Turborepo-шаблоны, Nx и др.).

## 5. Зачем нужен Turborepo (`turbo.json` и папка `.turbo`)

### 5.1. Проблема, которую он решает

У нас пять пакетов, и между ними есть **порядок сборки**. Например:

- `apps/api` использует `@repo/db`, а `@repo/db` перед использованием надо
  **сгенерировать** (`prisma generate`) и **собрать** (`tsc`).
- `apps/web` использует `@repo/shared`, а его тоже надо сначала собрать в `dist/`.

Если запустить сборку в неправильном порядке — приложение не найдёт свои библиотеки.
Запускать всё вручную и помнить порядок — больно. Вот тут и нужен **Turborepo**:
это «дирижёр задач» (task runner) для монорепо.

### 5.2. Что делает `turbo.json`

Это конфиг, в котором описано, **какие задачи существуют** и **что от чего зависит**.
Ключевое поле — `dependsOn`. Пример из нашего файла:

```json
"build": {
  "dependsOn": ["^build", "^db:generate"],
  "outputs": ["dist/**", ".next/**", "!.next/cache/**"]
}
```

Читается так:

- `^build` — «прежде чем собрать меня, собери всех, от кого я завишу»
  (значок `^` = «зависимости», upstream). То есть перед сборкой `api` Turbo сам
  соберёт `db` и `shared`.
- `^db:generate` — и точно так же сначала сгенерирует Prisma-клиент.
- `outputs` — что является результатом задачи (папки `dist`, `.next`). Это нужно для
  кэша (см. ниже).

Другой пример — `dev`:

```json
"dev": {
  "dependsOn": ["^build"],
  "cache": false,
  "persistent": true
}
```

`persistent: true` — задача «живёт долго» (сервер не завершается). `cache: false` —
её результат кэшировать бессмысленно. А `^build` гарантирует, что перед стартом
`web` и `api` библиотеки `shared`/`db` уже собраны — иначе `import "@repo/shared"`
упадёт. (Именно об этом предупреждает CLAUDE.md.)

### 5.3. Как это связано с корневыми скриптами

В корневом `package.json`:

```json
"scripts": {
  "dev":   "turbo run dev",
  "build": "turbo run build",
  "test":  "turbo run test"
}
```

Когда ты пишешь `npm run build`, запускается `turbo run build`, а Turbo:

1. Находит задачу `build` во всех воркспейсах, где она есть.
2. Строит граф зависимостей по `dependsOn`.
3. Запускает всё в правильном порядке и **параллельно там, где можно**
   (например, `shared` и `db` независимы — соберутся одновременно).

### 5.4. Папка `.turbo` — это кэш

`.turbo/` — это **кэш результатов задач** (плюс логи). Turbo запоминает: «для вот
такого набора входных файлов задача `build` дала вот такой результат». Если ты
запустишь `build` второй раз, ничего не поменяв, — Turbo **не будет пересобирать**,
а мгновенно достанет готовый результат из кэша. Это сильно ускоряет работу.

Папка создаётся автоматически и лежит в `.gitignore` — её не коммитят, у каждого
она своя. Удалить её безопасно: Turbo просто пересоберёт всё заново в следующий раз.

## 6. Docker Compose: `docker-compose.yml` и база данных

### 6.1. Что такое Docker и зачем он здесь

Нашему бэкенду нужна **база данных PostgreSQL** — место, где физически хранятся
расходы, категории и пользователи. PostgreSQL — это отдельная программа-сервер,
которую надо где-то запустить.

Можно установить PostgreSQL прямо на свой компьютер, но это неудобно: у тебя одна
версия, у коллеги другая, у сервера третья — и всё начинает вести себя по-разному.
Поэтому используют **Docker** — инструмент, который запускает программу внутри
**контейнера**: изолированной «коробки» с уже установленной, настроенной программой
нужной версии. Контейнер одинаково работает у всех.

**Docker Compose** — это надстройка над Docker, которая позволяет описать нужные
контейнеры в одном файле (`docker-compose.yml`) и поднять их одной командой:

```bash
docker compose up -d      # -d = в фоне (detached), терминал остаётся свободным
docker compose down       # остановить и удалить контейнер (данные при этом сохранятся, см. volume)
docker compose ps         # посмотреть, что запущено
docker compose logs -f    # смотреть логи контейнера
```

То есть `docker-compose.yml` отвечает на вопрос: «какая база данных, какой версии и
с какими настройками должна крутиться рядом с проектом» — и делает её запуск
воспроизводимым у всех.

### 6.2. Разбор нашего `docker-compose.yml` строка за строкой

```yaml
services:
  postgres:
    image: postgres:18-alpine
    container_name: expence-tracker-db
    restart: unless-stopped
    ports:
      - "${POSTGRES_PORT:-5433}:5432"
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-postgres}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-postgres}
      POSTGRES_DB: ${POSTGRES_DB:-expence_tracker}
    volumes:
      - postgres-data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-postgres} -d ${POSTGRES_DB:-expence_tracker}"]
      interval: 10s
      timeout: 5s
      retries: 5

volumes:
  postgres-data:
```

> 🔧 **Значения не захардкожены, а берутся из `.env`.** Синтаксис `${POSTGRES_USER}`
> — это **интерполяция** Docker Compose: при запуске `docker compose` он читает файл
> `.env` из корня проекта и подставляет значения. Запись `${POSTGRES_PORT:-5433}`
> означает «взять `POSTGRES_PORT`, а если её нет — использовать `5433`» (часть после
> `:-` — значение по умолчанию, чтобы контейнер поднялся даже без `.env`).
> Так `.env` становится **единым источником правды**: поменял пароль в одном месте —
> он применился и в контейнере, и в healthcheck. Проверить, что подставилось, можно
> командой `docker compose config` (она рендерит финальный конфиг без запуска).

Теперь по каждому блоку — что это, зачем и почему.

**`services:`** — список контейнеров, которыми управляет Compose. У нас он один и
называется `postgres`. (Если бы позже понадобился, скажем, Redis — он стал бы вторым
сервисом здесь же.)

**`image: postgres:18-alpine`** — из какого **образа** собирать контейнер. Образ —
это «заготовка» с уже установленной программой. `postgres` — официальный образ
PostgreSQL; `18` — мажорная версия; `alpine` — сборка на базе лёгкого дистрибутива
Alpine Linux (меньше весит, быстрее качается). Docker сам скачает образ из реестра
при первом запуске.

**`container_name: expence-tracker-db`** — человекочитаемое имя контейнера. Без него
Docker придумал бы имя сам. С ним удобно обращаться: `docker logs expence-tracker-db`.

**`restart: unless-stopped`** — политика перезапуска. Если контейнер упадёт или ты
перезагрузишь компьютер, Docker поднимет его снова **сам** — но только если ты не
остановил его вручную (`docker compose down`/`stop`). Удобно: база «всегда под рукой».

**`ports: - "${POSTGRES_PORT:-5433}:5432"`** — проброс портов, формат `ХОСТ:КОНТЕЙНЕР`.
Внутри контейнера PostgreSQL слушает свой стандартный порт `5432`. Наружу, на твой
компьютер (хост), мы выставляем его как `POSTGRES_PORT` (по умолчанию `5433`). Поэтому
в `DATABASE_URL` тоже стоит `5433`. Само значение хоста берётся из `.env`.

> ⚠️ **Почему именно 5433, а не привычный 5432** — это важная ловушка проекта.
> На хосте порт `5432` уже занимает локально установленная служба
> `postgresql-x64-18`. Windows при этом позволяет Docker-прокси «занять» тот же порт
> **молча**: контейнер выглядит здоровым и рапортует `0.0.0.0:5432->5432/tcp`, но
> подключения на `localhost:5432` уходят в локальную службу, а не в контейнер. Чтобы
> исключить путаницу («данные пропали», «таблиц нет»), контейнер публикуется на
> `5433`. Об этом же предупреждает `CLAUDE.md`.

**`environment:`** — переменные окружения, которые задают настройку PostgreSQL при
**первом** создании контейнера. Их значения подставляются из `.env`:
- `POSTGRES_USER: ${POSTGRES_USER}` — имя суперпользователя БД.
- `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}` — его пароль. (Для локальной разработки
  простой пароль ок; в проде так делать нельзя.)
- `POSTGRES_DB: ${POSTGRES_DB}` — имя базы, которую создать сразу при старте.

Эти же значения переиспользуются в `DATABASE_URL`, которая собирается из них прямо
в `.env`:
`DATABASE_URL="postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@${POSTGRES_HOST}:${POSTGRES_PORT}/${POSTGRES_DB}?schema=public"`.
`${VAR}` внутри строки разворачивает **dotenv-expand** (подключён в
`packages/db/prisma.config.ts`, в тестовом `test/test-db-url.ts` и в NestJS через
`ConfigModule.forRoot({ expandVariables: true })`). Так `POSTGRES_*` — **единственное**
место, где заданы логин/пароль/порт/имя БД: они питают и Docker, и строку подключения.

**`volumes: - postgres-data:/var/lib/postgresql`** — самый важный для сохранности
данных блок. Контейнеры **эфемерны**: удалил контейнер — исчезло всё, что было внутри.
Чтобы данные БД пережили пересоздание контейнера, мы монтируем **том** (volume) —
именованное хранилище, которым управляет Docker, — в ту папку внутри контейнера, где
PostgreSQL держит данные. Формат `ИМЯ_ТОМА:ПУТЬ_В_КОНТЕЙНЕРЕ`.

> Обрати внимание на путь: `/var/lib/postgresql`, **а не** привычный
> `/var/lib/postgresql/data`. В образе `postgres:18+` данные лежат в подкаталоге с
> именем мажорной версии, поэтому монтируют уровень выше. Это тоже отмечено в
> комментарии внутри самого `docker-compose.yml`.

Именно из-за тома `docker compose down` не стирает твои расходы: контейнер удаляется,
а том `postgres-data` остаётся. Чтобы удалить и данные тоже, нужен явный
`docker compose down -v` (`-v` = volumes) — **делай это осознанно**.

**`healthcheck:`** — как Docker понимает, что база не просто «запущена», а реально
**готова принимать подключения**. Команда `pg_isready` (с тем же `${POSTGRES_USER}`
и `${POSTGRES_DB}` из `.env`) периодически стучится в БД:
- `interval: 10s` — проверять каждые 10 секунд;
- `timeout: 5s` — ждать ответа не дольше 5 секунд;
- `retries: 5` — считать контейнер «нездоровым» после 5 неудач подряд.

Это защищает от гонки: PostgreSQL внутри поднимается не мгновенно, и без healthcheck
можно попытаться подключиться к ещё не готовой базе и получить ошибку.

**`volumes: postgres-data:`** (в самом низу, на верхнем уровне) — здесь том
**объявляется**. Верхний блок в `services` его *использует*, а этот — регистрирует у
Docker. Без этой строки Docker не знал бы про такой именованный том.

### 6.3. Как Docker связан с остальным проектом

Контейнер с PostgreSQL — это **не код приложения**, а его окружение. Связь такая:

```
.env: POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB / POSTGRES_HOST / POSTGRES_PORT
        │                                   │
        │ (Docker Compose ${...})           │ (dotenv-expand собирает DATABASE_URL)
        ▼                                   ▼
docker-compose.yml                    DATABASE_URL=postgresql://…@localhost:5433/expence_tracker
   поднимает PostgreSQL                     │
   на localhost:5433  ◀──────────────┐      ├──→ packages/db (Prisma): миграции, запросы
                                     └──────┴──→ apps/api (PrismaService): запросы к БД
```

Типичный порядок первого запуска:
1. `docker compose up -d` — подняли базу.
2. `npm run db:migrate` — Prisma создала таблицы (`users`, `categories`, `expenses`).
3. `npm run dev` — стартовали бэк и фронт, которые уже работают с живой базой.

Если что-то с данными «не сходится» — первым делом проверяй, что подключение идёт
именно в контейнер (`5433`), а не в локальную службу (`5432`).

## 7. Как это всё работает вместе — путь одного запроса

Чтобы связать всё воедино, проследим **реальный** путь, который уже работает
end-to-end: пользователь входит в систему. Он показывает и наши библиотеки, и
паттерн авторизации BFF (см. раздел 9).

Ключевая идея: **клиент никогда не видит JWT**. Браузер общается только со своим же
Next-сервером, а тот прячет токен в httpOnly-куку и сам ходит в Nest.

```
Браузер (apps/web)
   │  пользователь заполнил форму входа
   │  features/auth/login (react-hook-form + zodResolver ← loginSchema из @repo/shared)
   │  fetch POST /api/auth/login   ← СВОЙ же Next-сервер (same-origin), НЕ Nest напрямую
   ▼
Next Route Handler (BFF, apps/web/src/app/api/auth/login/route.ts)
   │  proxyAuth (shared/api/auth.server.ts) → nestFetch к Nest :3001/api/auth/login
   ▼
NestJS (apps/api)
   │  main.ts принял запрос (префикс /api, CORS разрешён)
   │  auth.controller.ts → auth.service.ts: queryBus GetUserByEmailQuery, сверка пароля (bcryptjs),
   │  подпись JWT (@nestjs/jwt). Тело валидируется loginSchema ← тот же @repo/shared
   ▼
Prisma (packages/db)
   │  prisma.service.ts → client.user.findUnique(...)            ← клиент из @repo/db
   ▼
PostgreSQL (docker, :5433)
   │  строка пользователя найдена
   ▼  Nest вернул { accessToken, user }
Next Route Handler
   │  кладёт accessToken в httpOnly-куку `session`, наружу отдаёт ТОЛЬКО { user }
   ▼
Браузер получает { user } (без токена!), редиректит на «/»; на «/» серверный layout
через getSession() валидирует куку запросом к Nest /auth/me и рисует «Вы вошли как …».
```

Обрати внимание, где всплывают наши библиотеки:

- **`@repo/shared`** — и фронт (`zodResolver` в форме), и бэк (валидация тела) используют
  одну и ту же `loginSchema` и типы (`UserDto`, `AuthResponseDto`). Никакого рассинхрона.
- **`@repo/db`** — бэк не создаёт Prisma-клиент сам, а берёт готовую фабрику из
  библиотеки. Единая точка настройки подключения.

> Путь для **расходов** будет такой же формы, но пока не собран на фронте: эндпоинты
> `/api/expenses` на стороне API готовы и закрыты `JwtAuthGuard` — `userId` берётся из
> токена (через `@CurrentUser()`), **а не** из query `?userId=` (тот удалён как дыра
> изоляции). Фронтовый клиент `shared/api/expenses.ts` пока временный и переключится на
> Bearer из сессии отдельной задачей. Денежная сумма `amount` при этом отдаётся наружу
> строкой (`toFixed(2)`), чтобы не терять копейки на JSON-числах.

Вот ради этого «переиспользования одного кода в разных местах» и затевается монорепо
с `packages/`, а Turborepo следит, чтобы всё собралось в правильном порядке.

## 9. Feature-Sliced Design и паттерн BFF (фронтенд)

Раздел 2 показал дерево `apps/web/src`. Здесь — **почему** оно так устроено.

### 9.1. Зачем слои (Feature-Sliced Design)

Раньше фронт был плоским (`lib/`, `components/`) — это ок для заглушки, но с ростом
превращается в кашу: непонятно, что от чего зависит и что можно менять безопасно.
**Feature-Sliced Design (FSD)** наводит порядок: код делится на слои, и импорт разрешён
**только вниз** — слой видит нижние, но не верхние и не соседей своего уровня.

```
app       ← маршруты Next и BFF Route Handlers (тонкие обёртки)
views     ← страницы-композиции (FSD-слой «pages» переименован: «pages» занят Next)
widgets   ← самостоятельные блоки (напр. auth-status)
features  ← пользовательские сценарии (auth/login, auth/register, auth/logout)
entities  ← бизнес-сущности (session)
shared    ← ui (shadcn), lib, api, config — переиспользуемое, без домена
```

Правило «импорт только вниз» — то же, что между `apps/` и `packages/` (раздел 4), но
уже **внутри** фронта. Оно не даёт зависимостям запутаться. Наружу слайс общается через
свой `index.ts` (публичный API), внутри — сегменты `ui/`, `model/`, `api/`, `config/`.
Алиас `@/* → src/*`.

Пара адаптаций под Next App Router:
- FSD-слой «pages» назван **`views`**, потому что слово «pages» занято самим Next.
- `src/app` держит только маршруты и BFF-хендлеры и делегирует в `views`; провайдеры
  сведены в корневой серверный `layout.tsx`.
- shadcn/ui живёт в `shared/ui` (алиасы в `components.json` перенастроены на `@/shared/*`).

### 9.2. Зачем BFF и httpOnly-кука (безопасность токена)

**BFF = Backend For Frontend.** Идея: браузер общается не с Nest напрямую, а со своим же
Next-сервером, а тот уже ходит в Nest. Зачем усложнять? Ради **безопасности JWT**.

Если положить токен в `localStorage` или в обычную куку, до него дотянется любой скрипт
на странице (в т.ч. вредный — XSS) и украдёт. Поэтому:

- Форма входа шлёт запрос на **свой** Route Handler (`POST /api/auth/login`, same-origin).
- Хендлер ходит в Nest, получает `accessToken` и кладёт его в **httpOnly-куку** `session`.
  `httpOnly` значит «JavaScript эту куку не видит» — её отправляет только браузер и только
  на наш сервер. Наружу, в браузерный JS, хендлер отдаёт **только** `{ user }`, без токена.
- Дальше на каждый серверный рендер `getSession()` (только сервер, помечен `server-only`)
  читает куку и валидирует её запросом к Nest `/auth/me` (юзер мог быть удалён, пока жив
  7-дневный токен) → `UserDto` либо `null`.

Так JWT **никогда** не попадает в клиентский JavaScript — украсть нечего.

> Граница «сервер/клиент» строгая: серверные модули помечены `import "server-only"` и не
> реэкспортируются через клиентский `index.ts` слайса (для `session` серверный вход —
> отдельный `server.ts`). `shared/api/nest.ts` — тоже только сервер.

### 9.3. Редирект залогиненного со страниц входа — на самой странице

Залогиненного пользователя со страниц `/login` и `/register` уводит на `/` **гард в самих
серверных `page.tsx`** (`if (await getSession()) redirect("/")`), а **не** middleware/proxy.

Почему не middleware: он проверял бы только **наличие** куки, а `getSession()` — её
**валидность**. Протухшая кука (например, после смены `JWT_SECRET`) иначе давала петлю
редиректов `/login → / → /login` и тормозила навигацию блокирующим сетевым вызовом на
каждый запрос. Источник истины один — `getSession`. (Подробности — в `CLAUDE.md`.)

## 10. Мини-словарь терминов

- **Монорепо** — один репозиторий с несколькими проектами внутри.
- **Workspace (воркспейс)** — один пакет внутри монорепо (у нас их 4 + корень).
- **Hoisting** — подъём зависимостей в общую корневую `node_modules`.
- **Символическая ссылка** — «ярлык» на папку; так `node_modules/@repo/db`
  указывает на `packages/db`.
- **Task runner** — инструмент, запускающий задачи в правильном порядке (Turborepo).
- **`dependsOn` / `^`** — «сначала выполни у зависимостей, потом у меня».
- **DTO** — Data Transfer Object, объект-описание данных, которыми обмениваются
  фронт и бэк (`ExpenseDto` в `@repo/shared`).
- **Миграция** — записанное в SQL изменение структуры БД (папка `prisma/migrations`).
- **Driver adapter** — обязательная в Prisma 7 прослойка между клиентом и драйвером
  PostgreSQL (`PrismaPg` в `packages/db/src/client.ts`).
- **Контейнер** — изолированная «коробка», в которой запущена программа (у нас —
  PostgreSQL) в нужной версии и настройке, одинаково у всех.
- **Образ (image)** — «заготовка» контейнера с уже установленной программой
  (`postgres:18-alpine`); из образа создаются контейнеры.
- **Том (volume)** — постоянное хранилище Docker (`postgres-data`), которое переживает
  пересоздание контейнера; благодаря ему данные БД не пропадают.
- **Проброс портов** — правило `ХОСТ:КОНТЕЙНЕР` (`5433:5432`), связывающее порт внутри
  контейнера с портом на твоём компьютере.
- **Healthcheck** — периодическая проверка, что сервис в контейнере готов принимать
  подключения (`pg_isready`).
- **Feature-Sliced Design (FSD)** — способ организации фронта по слоям
  (`app → views → widgets → features → entities → shared`) с импортом только вниз.
- **BFF (Backend For Frontend)** — свой серверный слой между браузером и Nest
  (Next Route Handlers `app/api/auth/*`), который прячет JWT и отдаёт клиенту только `{ user }`.
- **httpOnly-кука** — кука, недоступная браузерному JavaScript; в ней лежит JWT
  (`session`), поэтому его нельзя украсть скриптом на странице.
- **`server-only`** — маркер-импорт, запрещающий тянуть серверный модуль в клиентский
  бандл; так `getSession()` и клиенты к Nest не утекают на клиент.
