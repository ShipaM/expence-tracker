## Что делает

Разбирает переданный файл, пишет для него юнит-тесты `*.spec.ts` рядом с кодом и прогоняет их
в его воркспейсе, пока они не станут зелёными. Вызывается вручную: `/unit-tests <путь>`.

Аргументом можно передать **папку** — тогда скилл покрывает все подходящие файлы внутри,
по одному за раз (см. «Режим папки»).

Тесты — юнит: без БД, без поднятого API, без сети. Всё внешнее мокается.

## Аргументы

```
/unit-tests <path> [<фокус>]
```

| Аргумент | Обязателен | Смысл                                                                          |
| -------- | ---------- | ------------------------------------------------------------------------------ |
| `path`   | **да**     | **файл или папка**; путь от корня монорепо                                     |
| `фокус`  | нет        | что покрыть в первую очередь (метод, сценарий); если не задан — весь файл      |

Примеры:

```
/unit-tests apps/api/src/payments/payments.service.ts
/unit-tests packages/shared/src/index.ts "схема createTransactionSchema"
/unit-tests apps/web/src/shared/ui                 # вся папка компонентов
/unit-tests apps/api/src/transactions              # весь модуль (сервис; контроллер и dto — мимо)
```

Если `path` не передан — не угадывать файл, а спросить пользователя.

В режиме папки `фокус` относится ко всем файлам сразу («только счастливые пути», «сосредоточься
на валидации»), а не к одному.

## Где тесты вообще возможны

| Воркспейс         | Тестовая инфраструктура                            | Что делать                                       |
| ----------------- | -------------------------------------------------- | ------------------------------------------------ |
| `apps/api`        | Vitest + `unplugin-swc`, окружение `node`          | писать `*.spec.ts` рядом с файлом                |
| `packages/shared` | Vitest, окружение `node`                           | писать `*.spec.ts` рядом с файлом                |
| `apps/web`        | Vitest + Testing Library, окружение `jsdom`        | писать `*.spec.tsx` рядом с компонентом          |
| `packages/db`     | нет                                                | остановиться: там схема и сгенерированный клиент |

Инфраструктуру тестов (установку `vitest`, конфиг, скрипт `test` в `package.json`) этот скилл
**не поднимает** — это отдельная задача, её решает пользователь.

## Что тестировать, а что нет

Юнитами покрывается логика: сервисы Nest, zod-схемы в `packages/shared`, чистые функции и хелперы,
компоненты и хуки в `apps/web`.

Не писать юниты на: `*.module.ts` и `main.ts` (исключены из coverage), DTO-классы
class-validator, контроллеры и guard'ы — HTTP-слой и авторизация покрыты e2e в
`apps/api/test/*.e2e-spec.ts`. На фронте не покрывать юнитами серверные модули (`server-only`,
`getSession`, BFF Route Handlers в `src/app/api/**`) — они требуют рантайма Next. Если переданный
файл из этого списка — сказать об этом и предложить e2e вместо юнита, а не писать пустой тест ради
галочки.

## Режим папки

Если `path` — папка, скилл покрывает **все подходящие файлы внутри, включая вложенные**.

### 1. Собрать кандидатов

`Glob` по `<path>/**/*.{ts,tsx}` — он же покажет вложенные папки. `ls -R <path>` годится, когда
надо просто глазами увидеть структуру.

### 2. Отсеять неподходящее

Из списка выкидываются, **без исключений**:

| Что                                     | Почему                                                    |
| --------------------------------------- | ---------------------------------------------------------- |
| `*.spec.ts` / `*.spec.tsx`              | это сами тесты                                            |
| `index.ts` слайса                       | только реэкспорты, тестировать нечего                     |
| `*.module.ts`, `main.ts`                | исключены из coverage                                     |
| `*.controller.ts`, `*.guard.ts`         | HTTP-слой и авторизация — покрыты e2e                     |
| `dto/**`, `contracts/**`                | классы-данные без поведения                               |
| `src/app/**`, файлы с `import "server-only"` | требуют рантайма Next                                |
| `*.d.ts`, `*.config.ts`                 | типы и конфигурация                                       |

Файл, где нет ни одного экспорта с поведением (только типы, только константы) — тоже мимо.

### 3. Показать план и получить добро

Перед тем как писать первый тест, вывести пользователю два списка — **что покрою** и **что
пропущу с причиной**, и дождаться подтверждения. Оценку кейсов не выдумывать, если файл ещё
не прочитан, — достаточно перечня файлов.

**Если файлов больше восьми** — предупредить, что это надолго, и предложить сузить: подпапкой
или частями. Молча уходить в получасовой прогон нельзя.

### 4. Идти строго по одному файлу

Для каждого кандидата: прочитать → написать spec → **прогнать именно его** → зелёный → следующий.

Не писать все spec'и разом и не запускать их одним прогоном в конце: при падении будет
непонятно, какой из десяти новых файлов виноват, и разбор превратится в кашу.

После каждого файла — строчка прогресса: `[3/7] card.tsx → 17 кейсов, зелёные`.

### 5. Уже покрытые файлы — пропускать

Если рядом с файлом уже лежит его spec — в режиме папки **не трогать его**, а отметить в сводке
как пропущенный. Дополнять существующие тесты имеет смысл прицельно, поэтому это делается
отдельным вызовом на конкретный файл (`/unit-tests <файл>`), где видно, что именно добавляется.

### 6. Сводка — таблицей

```markdown
| Файл          | Кейсов | Статус                        |
| ------------- | ------ | ----------------------------- |
| button.tsx    | —      | пропущен: spec уже есть       |
| card.tsx      | 17     | ✓                             |
| checkbox.tsx  | 9      | ✓                             |
| form.tsx      | —      | пропущен: реэкспорты RHF      |
```

Плюс итог по воркспейсу: сколько файлов покрыто, сколько тестов всего, результат общего прогона.

## Алгоритм выполнения

Ниже — путь для одного файла. Если передана папка, сначала отработать «Режим папки»
(собрать список, показать план, получить добро), а потом пройти эти шаги для каждого файла
по очереди.

1. **Определить, файл это или папка,** и вычислить воркспейс по пути. Путь из `packages/db` →
   остановиться (см. таблицу выше). Затем прочитать целевой файл целиком.

2. **Проверить, есть ли уже spec:** `<имя>.spec.ts(x)` рядом. Для одиночного файла — **дополнять
   его**, а не перезаписывать: новые `describe`/`it` в существующую структуру, чужие кейсы не
   трогать. В режиме папки — пропустить файл и отметить в сводке.

3. **Посмотреть соседний spec как образец** — конвенции проекта видны в них, а не в общих
   рекомендациях Vitest:

   ```bash
   ls apps/api/src/*/*.spec.ts
   ```

   `categories.service.spec.ts` — сервис с моком Prisma и `QueryBus`;
   `auth.service.spec.ts` — моки `CommandBus`/`QueryBus`/`JwtService`;
   `transactions.service.spec.ts` — денежные суммы через реальный `Prisma.Decimal`;
   `packages/shared/src/index.spec.ts` — zod-схемы через `safeParse` и `it.each`;
   `apps/web/src/shared/ui/button.spec.tsx` — компонент: роли, data-атрибуты, `userEvent`.

4. **Разобрать зависимости целевого файла** — что инжектится в конструктор, что придётся мокать,
   какие ветки есть у каждого публичного метода (успех, «не найдено», «чужой пользователь»,
   ошибка Prisma).

5. **Написать spec** по шаблону ниже. Покрыть по каждому публичному методу минимум:
   счастливый путь, каждую ветку с брошенным исключением, граничные значения.

6. **Прогнать только этот файл** — внутри воркспейса, иначе Turbo раздаст аргумент всем задачам:

   ```bash
   npm run test --workspace @repo/api -- src/payments/payments.service.spec.ts
   npm run test --workspace @repo/shared -- src/index.spec.ts
   npm run test --workspace @repo/web -- src/shared/ui/button.spec.tsx
   ```

   Путь после `--` — относительно воркспейса, а не корня монорепо.

7. **Чинить до зелёного — тест, а не исходник.** Если тест падает, потому что в коде реальная
   ошибка, — не править код молча: показать пользователю падение и спросить, чинить ли исходник.
   В режиме папки не копить падения «на потом»: файл либо зелёный, либо разбираемся сейчас.

8. **Прогнать весь воркспейс,** чтобы убедиться, что ничего не сломано соседям (в режиме папки —
   один раз в конце, а не после каждого файла):

   ```bash
   npm run test --workspace @repo/api
   ```

9. **Вывести сводку:** какой файл покрыт, сколько кейсов добавлено, что осталось непокрытым и
   почему (например, ветка достижима только через HTTP → e2e). Для папки — таблицей, см.
   «Режим папки».

## Конвенции тестов проекта

- **Имя и место:** `<имя-файла>.spec.ts` рядом с исходником, никакой папки `__tests__`.
- **Импорты из `vitest` — явные** (`import { beforeEach, describe, expect, it, vi } from "vitest"`),
  хотя `globals: true` включён: так написаны все существующие spec'и.
- **Названия кейсов — на русском**, по факту поведения: «бросает 404, если категория принадлежит
  другому пользователю», а не «should throw».
- **Сервисы Nest — через `Test.createTestingModule`** с подменой провайдеров на моки
  (`{ provide: PrismaService, useValue: prismaMock }`), а не через `new Service(...)`.
- **`PrismaService` содержит клиент, а не наследует его** — мок повторяет структуру
  `{ client: { transaction: { findMany: vi.fn(), ... } } }`.
- **Границы модулей — через шину.** Users ↔ Auth и проверка пользователя в
  `categories`/`transactions` идут через `CommandBus`/`QueryBus`; в тестах мокается шина и
  проверяется, что ушла нужная команда/запрос, а не то, что дёрнулся чужой сервис.
- **Денежные суммы — реальный `Prisma.Decimal`,** не `number` и не строка: у сервисов вызываются
  `toFixed`/`minus`. Наружу сервис отдаёт строки (`amount.toFixed(2)`) — так и проверять.
- **`vi.clearAllMocks()` в `beforeEach`** — моки объявлены на уровне модуля и переживают кейсы.
- **Ошибки Prisma мокаются утиным объектом** (`{ code: "P2002" }`): сервис проверяет код, а не
  класс ошибки, и тест не должен завязываться на путь импорта.
- **Без БД, сети и таймеров реального времени.** Если тест требует базу — это e2e, а не юнит.

### Компоненты `apps/web`

- **Имя — `<компонент>.spec.tsx`** рядом с компонентом; окружение `jsdom` уже задано в конфиге.
- **Искать по роли и доступному имени** (`screen.getByRole("button", { name: "Сохранить" })`),
  а не по тексту или тестовым id: тест тогда проверяет то же, что видит пользователь.
- **Не проверять Tailwind-классы там, где есть data-атрибут.** Компоненты shadcn проставляют
  `data-slot`/`data-variant`/`data-size` — на них и опираться. Класс проверять только когда
  смысл именно в нём (например, что `twMerge` вытеснил конфликтующий класс).
- **Взаимодействие — через `userEvent`**, а не `fireEvent`: он ближе к реальному вводу и сам
  ждёт перерисовку. Вызовы `await`-ить.
- **`cleanup()` уже висит в `afterEach`** (`vitest.setup.ts`) — в тестах его не дублировать.

## Шаблон spec для сервиса Nest

```ts
import { Test } from "@nestjs/testing";
import { NotFoundException } from "@nestjs/common";
import { beforeEach, describe, expect, it, vi } from "vitest";
import { PrismaService } from "../prisma/prisma.service";
import { SomeService } from "./some.service";

const USER_ID = "b292ff2b-db0a-44bf-aa4a-b4e6fc353283";

const prismaMock = {
  client: {
    someEntity: { findMany: vi.fn(), findFirst: vi.fn(), create: vi.fn() },
  },
};

describe("SomeService", () => {
  let service: SomeService;

  beforeEach(async () => {
    vi.clearAllMocks();

    const moduleRef = await Test.createTestingModule({
      providers: [SomeService, { provide: PrismaService, useValue: prismaMock }],
    }).compile();

    service = moduleRef.get(SomeService);
  });

  describe("findOne", () => {
    it("бросает 404, если запись принадлежит другому пользователю", async () => {
      prismaMock.client.someEntity.findFirst.mockResolvedValue(null);

      await expect(service.findOne(USER_ID, "id")).rejects.toThrow(NotFoundException);
    });
  });
});
```

## Если тесты не запускаются

- Типы из `@repo/db` не резолвятся (свежий клон, после `npm run clean`) → `npm run db:generate`.
- DI в тесте молча ломается, зависимости `undefined` → проверить, что в
  `apps/api/vitest.config.ts` остались `oxc: false` и плагин `unplugin-swc`: Oxc не умеет
  `emitDecoratorMetadata`. Не «чинить» это удалением строк из конфига.
- Тест `web` падает на синтаксисе JSX → в `apps/web/vitest.config.ts` пропал
  `@vitejs/plugin-react`: в `tsconfig` стоит `jsx: "preserve"`, сам Vitest JSX не соберёт.
- Импорт `@/...` в тесте `web` не резолвится → `resolve.alias` в конфиге; `paths` из `tsconfig`
  Vitest не читает.

## Запрещено

- Не менять тестируемый исходник, чтобы тест позеленел, без явного согласия пользователя.
- Не перезаписывать существующий spec-файл целиком — только дополнять.
- В режиме папки не уходить в работу молча: сначала список файлов и подтверждение, и тем более
  не начинать без спроса, когда кандидатов больше восьми.
- Не писать пачку spec'ов «вслепую», отложив прогон на конец: каждый файл проверяется сразу.
- Не растягивать охват за пределы переданной папки — соседние слайсы не трогать.
- Не поднимать тестовую инфраструктуру там, где её нет (`packages/db`), и не ставить пакеты.
- Не писать тесты, требующие БД, контейнера или живого API, — это e2e.
- Не запускать `npm test` с аргументом файла из корня: Turbo передаст его всем воркспейсам.
- Не трогать `vitest.config.ts` / `vitest.config.e2e.ts` и не коммитить результат — коммит делает
  скилл `commit` по просьбе пользователя.
