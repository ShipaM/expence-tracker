## Что делает

Собирает коммиты за **вчерашний день** по всем веткам и превращает их в отчёт для устного
стендапа: не список сообщений коммитов, а связный рассказ — что сделано, где и зачем.

Вызывается вручную: `/standup`. Модель сама скилл не запускает.

## Аргументы (необязательные)

| Аргумент     | Смысл                                  |
| ------------ | -------------------------------------- |
| _(пусто)_    | вчерашний день, только свои коммиты    |
| `today`      | сегодняшний день вместо вчерашнего     |
| `week`       | последние 7 дней                       |
| `YYYY-MM-DD` | конкретная дата                        |
| `all`        | коммиты всех авторов, а не только свои |

Комбинируются: `/standup week all`.

## Алгоритм выполнения

1. **Определить период.** Границы считать через `date`, не полагаться на `git log --since="yesterday"`
   (git трактует это как «24 часа назад», а не как календарный день):

   ```bash
   FROM=$(date -d yesterday +%F)   # today → $(date +%F); week → $(date -d '7 days ago' +%F)
   TO=$(date +%F)
   ```

2. **Собрать коммиты** — по всем веткам (`--all`, работа могла идти в feature-ветке) и по
   умолчанию только свои:

   ```bash
   git log --all --no-merges --author="$(git config user.name)" \
     --since="$FROM 00:00" --until="$TO 00:00" \
     --date=format:'%H:%M' --pretty=format:'%h %ad %d %s'
   ```

3. **Если за период коммитов нет** — не выдумывать и не отдавать пустой отчёт: расширить окно до
   последних 7 дней, взять последний день с активностью и **явно написать в отчёте**, что это за
   день («вчера коммитов не было, последняя работа — <дата>»).

4. **Разобрать содержимое.** По каждому коммиту посмотреть, что реально менялось, — без этого
   отчёт выродится в пересказ заголовков:

   ```bash
   git show --stat --oneline <sha>     # состав: какие файлы, объём
   git show <sha> -- <важный файл>     # детали, если из статистики непонятно
   ```

   Обращать внимание на: новые модули/слайсы FSD, изменения схемы Prisma и миграции, новые или
   изменённые эндпоинты, тесты, правки конфигов и документации.

5. **Сгруппировать по задачам, а не по коммитам.** Три коммита про одну фичу — один пункт отчёта.
   Для каждого пункта: что сделано → в какой части проекта (web / api / db / shared / config) →
   зачем, если это видно из кода.

6. **Добавить незавершённое.** `git status --short` и `git log origin/master..HEAD --oneline` —
   что лежит в рабочем дереве и что уже в ветке, но ещё не влито в `master`.

7. **Вывести отчёт** в формате ниже.

## Формат вывода

```markdown
## Стендап за <дата>, <день недели>

### Сделано

- **<Область>: <краткая суть>** — <2–3 предложения: что именно изменилось и зачем> (`<sha>`, `<sha>`)
- ...

### В работе

- <незакоммиченные изменения из git status и невлитые ветки; если чисто — «рабочее дерево чистое»>

### Блокеры

- <только если видны из кода: упавшие тесты, TODO/FIXME в новом коде, помеченные заглушки;
  если не видно — «нет»>

---

<N> коммитов · <M> файлов · +<A>/−<B> строк · ветки: <список>
```

Отчёт — на английском, названия файлов, веток и идентификаторы — как есть. Пункты формулировать так,
чтобы их можно было зачитать вслух за 30–60 секунд.

## Запрещено

- Ничего не коммитить, не пушить и не переключать ветки — скилл только читает историю.
- Не пересказывать сообщения коммитов дословно: отчёт про смысл работы, а не про `git log`.
- Не додумывать задачи, тикеты и оценки, которых нет в истории и в рабочем дереве.
- Не подставлять в отчёт коммиты чужих авторов без аргумента `all`.
